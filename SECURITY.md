# Безопасность FlautCompany

Этот документ описывает общий подход **FlautCompany** к информационной безопасности и взаимосвязь технологий, разработанных подразделением **FlautSecurity**.

Основной принцип архитектуры — не пытаться решить все проблемы одним механизмом.

В экосистеме FlautCompany безопасность разделяется как минимум на два уровня:

```text
┌─────────────────────────────────────────┐
│              Приложение                 │
│                                         │
│   ┌─────────────────────────────────┐   │
│   │           FlautGuard             │   │
│   │         AI Security Layer        │   │
│   └─────────────────────────────────┘   │
│                    │                    │
│                    ▼                    │
│                  LLM                   │
│                                         │
│   ┌─────────────────────────────────┐   │
│   │            .fsecurity            │   │
│   │          Data Security            │   │
│   └─────────────────────────────────┘   │
│                    │                    │
│                    ▼                    │
│             Зашифрованные данные        │
└─────────────────────────────────────────┘
```

`.fsecurity` отвечает за защиту данных.

FlautGuard отвечает за дополнительную защиту AI-систем.

---

# 1. Защита данных: .fsecurity

`.fsecurity` — программный криптографический модуль, разработанный FlautSecurity.

Он интегрируется непосредственно в приложение и предназначен для шифрования данных до их сохранения в постоянное хранилище.

Модуль может использоваться для защиты:

* пользовательских файлов;
* запросов;
* ответов;
* логов;
* метаданных;
* сессий;
* других данных приложения.

В реализации используется **AES-256-GCM**.

---

## Изоляция данных

Одна из архитектурных целей `.fsecurity` — минимизировать последствия компрометации отдельного объекта или хранилища.

Каждый защищаемый объект может иметь собственный криптографический ключ.

Упрощённая модель:

```text
Файл A ──► Key A ──► AES-256-GCM ──► Ciphertext A

Файл B ──► Key B ──► AES-256-GCM ──► Ciphertext B

Файл C ──► Key C ──► AES-256-GCM ──► Ciphertext C
```

Поэтому получение одного ключа не должно автоматически предоставлять доступ ко всем остальным объектам.

---

# 2. Защита AI: FlautGuard

Современная AI-система имеет собственную поверхность атаки.

Пользователь может попытаться не только получить несанкционированный доступ к данным, но и изменить поведение модели специально сформированным запросом.

Поэтому FlautSecurity использует отдельный уровень защиты — **FlautGuard**.

FlautGuard обрабатывает данные до передачи модели и после формирования ответа.

```text
Запрос
  │
  ▼
CleanIn
  │
  ▼
DetectIn
  │
  ▼
LLM
  │
  ▼
FilterOut
  │
  ▼
Ответ
```

Дополнительный защитный контур формируется посредством `ShieldIn`.

---

# 3. Модель угроз

FlautGuard ориентирован на угрозы, специфичные для систем искусственного интеллекта.

В частности:

### Prompt injection

Пользователь пытается заставить модель игнорировать первоначальные инструкции или выполнить инструкции из пользовательского ввода.

### Adversarial input

Атакующий изменяет форму запроса таким образом, чтобы обойти фильтры или изменить поведение системы.

### Data leakage

Модель может сформировать ответ, содержащий чувствительную информацию.

### Обход фильтров

Атакующий может использовать Unicode, форматирование, разбиение текста и другие особенности представления данных для обхода защитных механизмов.

Эти угрозы требуют разных методов защиты, поэтому FlautGuard использует несколько последовательных уровней.

---

# 4. CleanIn

`CleanIn` выполняет нормализацию входного текста.

Задача слоя — уменьшить количество вариантов представления одного и того же запроса.

В зависимости от реализации могут анализироваться:

* Unicode;
* управляющие символы;
* нестандартное форматирование;
* повторяющиеся последовательности;
* различные варианты кодирования;
* структура входного текста.

После нормализации данные передаются в DetectIn.

---

# 5. DetectIn

`DetectIn` отвечает за классификацию входного запроса.

Основной класс обнаруживаемых атак — prompt injection.

Упрощённо:

```text
Input
 │
 ▼
DetectIn
 │
 ├── normal ──────► LLM
 │
 └── suspicious ──► security policy
```

Классификатор не должен рассматриваться как единственная линия защиты.

Причина проста: классификатор сам по себе является вероятностным механизмом и может ошибаться.

Поэтому DetectIn является одним из уровней FlautGuard, а не всей системой безопасности.

---

# 6. ShieldIn

`ShieldIn` предназначен для дополнительного контроля AI-контура.

В отличие от внешнего классификатора, этот слой располагается ближе к обработке самой моделью.

Задача ShieldIn — добавить дополнительный механизм контроля, который не зависит исключительно от анализа пользовательского текста.

Такой подход позволяет строить защиту по принципу нескольких независимых барьеров.

---

# 7. FilterOut

Даже если входной запрос прошёл все проверки, конечный ответ модели также необходимо контролировать.

Именно для этого используется `FilterOut`.

Он анализирует сформированный моделью ответ перед передачей пользователю.

Возможные механизмы анализа:

* NER;
* регулярные выражения;
* правила обнаружения чувствительных данных;
* контекстные проверки;
* политики обработки определённых типов информации.

Упрощённая схема:

```text
LLM response
     │
     ▼
 FilterOut
     │
 ┌───┴────┐
 ▼        ▼
allow    block/process
```

Это позволяет создавать защиту не только от вредоносного ввода, но и от потенциальных утечек через ответ модели.

---

# 8. Почему два уровня лучше одного

`.fsecurity` и FlautGuard решают разные задачи.

Если атакующий пытается получить данные из хранилища, основным уровнем защиты является `.fsecurity`.

Если атакующий пытается манипулировать моделью через пользовательский ввод, основным уровнем защиты является FlautGuard.

Таким образом:

```text
                 Атака
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
       Данные              AI
          │                 │
          ▼                 ▼
    .fsecurity          FlautGuard
          │                 │
          ▼                 ▼
     Data Security       AI Security
```

Это разделение позволяет не использовать один механизм для решения принципиально разных задач.

---

# 9. Принцип минимизации последствий

Безопасность должна учитывать не только вероятность атаки, но и последствия успешной атаки.

Например, если один объект данных оказался скомпрометирован, архитектура должна препятствовать автоматическому распространению компрометации на остальные объекты.

Аналогично AI-защита должна состоять из нескольких независимых этапов, чтобы ошибка одного фильтра не означала автоматический обход всей системы.

Поэтому FlautSecurity использует многоуровневую модель.

---

# 10. Границы защиты

Ни `.fsecurity`, ни FlautGuard не являются универсальным решением всех проблем информационной безопасности.

Безопасность конечной системы также зависит от:

* конфигурации сервера;
* управления доступом;
* безопасности операционной системы;
* защиты инфраструктуры;
* управления секретами;
* безопасности зависимостей;
* правильности реализации приложения;
* политики доступа пользователей;
* мониторинга и реагирования на инциденты.

Криптографический модуль не исправляет уязвимость бизнес-логики.

AI-фильтр не заменяет полноценную модель угроз.

Именно поэтому технологии FlautSecurity рассматриваются как отдельные уровни общей архитектуры безопасности.

---

# 11. Общая модель

Систему можно представить как последовательность уровней:

```text
                    Пользователь
                         │
                         ▼
                  ┌─────────────┐
                  │  FlautGuard │
                  └──────┬──────┘
                         │
                         ▼
                        LLM
                         │
                         ▼
                  ┌─────────────┐
                  │  FlautGuard │
                  │  FilterOut  │
                  └──────┬──────┘
                         │
                         ▼
                    Приложение
                         │
                         ▼
                  ┌─────────────┐
                  │ .fsecurity  │
                  └──────┬──────┘
                         │
                         ▼
                Зашифрованные данные
```

Таким образом, защита разделяется на два принципиальных слоя:

**FlautGuard → безопасность AI-взаимодействия**

**`.fsecurity` → безопасность данных**

---

# 12. Подход FlautSecurity

FlautSecurity рассматривает безопасность как архитектурную задачу, а не как отдельный фильтр или библиотеку.

Разные классы угроз требуют разных механизмов защиты.

Поэтому технологии FlautSecurity развиваются как взаимодополняющие компоненты:

```text
FlautSecurity
│
├── .fsecurity
│      └── защита данных
│
└── FlautGuard
       └── защита AI
```

Оба уровня могут существовать независимо, но при совместном использовании формируют более комплексную модель защиты приложения.
